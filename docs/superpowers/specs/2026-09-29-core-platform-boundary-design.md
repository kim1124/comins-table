# Comins Table 0.2.0 Core 플랫폼 경계 설계

## 1. 결론

Comins Table 0.2.0은 현재 `codex-0.2.0-core-separation` 브랜치 하나에서 Core 분리와 React 어댑터 리팩터링을 완료한다. 하위 작업마다 별도 브랜치를 추가하지 않고, 검토 가능한 원자적 커밋과 단계별 검증으로 진행한다.

Vue 3 지원은 0.2.0 범위에서 제외한다. 0.2.0이 `main`에 통합되고 배포된 뒤, 확정된 Core 계약을 기준으로 후속 버전 설계를 시작한다. 동일 패키지에 Vue 진입점을 추가한다면 기본 후보 버전은 0.3.0이며, 실제 패키지 구조와 버전은 Vue 설계 단계에서 확정한다.

## 2. 배경과 현재 상태

- `main`은 배포 중인 0.1.x React 제품선이다.
- `codex-0.2.0-core-separation`은 다중 프레임워크 지원을 위한 0.2.0 통합 브랜치다.
- 1단계에서는 공유 타입과 React 전용 타입을 분리하고, UI에 있던 순수 계산 일부를 Core 쪽으로 이동했다.
- 현재 공개 진입점은 `comins-table`, `comins-table/core`, `comins-table/clipboard`, `comins-table/selection`, `comins-table/styles.css`다.
- 현재 `/core` 경계에는 React 전용 타입과의 결합이 남아 있어, Vue 어댑터가 직접 사용할 수 있는 프레임워크 중립 계약으로 보기는 어렵다.

## 3. 목표

0.2.0의 목표는 다음과 같다.

1. `comins-table/core`의 공개 런타임과 타입 계약에서 React 의존성을 제거한다.
2. 기존 React 공개 API와 사용자 동작을 React 어댑터 계층에서 유지한다.
3. 상태, 컬럼 모델, 선택, 정렬, 필터, 그룹화, 가상화 계산 등 프레임워크와 무관한 책임의 소유권을 Core에 둔다.
4. 후속 Vue 어댑터가 React 내부 구현을 재사용하지 않고 Core 계약만 사용할 수 있게 한다.
5. 0.2.0의 호환성 변경과 마이그레이션 경로를 영어·한국어 문서에 명시한다.

## 4. 제외 범위

다음 항목은 0.2.0에서 수행하지 않는다.

- Vue 3 컴포넌트, Vue 전용 타입, Vue 의존성, Vue 예제 및 Vue 문서 구현
- 별도 Core npm 패키지 발행 또는 모노레포 전환
- 공개 진입점의 불필요한 변경 또는 제거
- Core 분리와 무관한 기능 추가, 알고리즘 교체, UI 재설계
- 원격 push, PR 생성·병합, npm 배포, 태그 및 Release 생성

별도 Core npm 패키지는 장기적으로 검토할 수 있으나, 0.2.0에서는 단일 `comins-table` 패키지 안의 모듈 경계로 독립성을 확보한다. 따라서 0.2.0의 `/core`는 코드와 타입 수준에서 React와 독립적이어야 하지만, 패키지 설치 단위까지 React peer dependency와 분리하는 것은 목표가 아니다.

## 5. 목표 아키텍처

### 5.1 Core 계층

Core는 다음 책임만 소유한다.

- 행·컬럼 식별자와 데이터 접근 계약
- 프레임워크 중립 컬럼 모델
- 정렬, 필터, 그룹화, 선택, 확장, 편집 상태의 데이터 계약과 상태 전이
- 행 모델 생성과 가상화·스크롤 관련 순수 계산
- 상태 정규화와 외부 제어 상태 조정
- DOM, JSX, React 노드 또는 프레임워크 생명주기가 필요 없는 유틸리티

`src/core.ts`에서 공개하는 모든 값과 타입은 다음 조건을 만족해야 한다.

- `react`, `react-dom`, JSX 런타임을 import하지 않는다.
- 생성된 선언 파일이 React 타입을 참조하지 않는다.
- DOM 노드, React 이벤트, React 렌더러 타입을 공개 Core 계약에 포함하지 않는다.
- 순수 입력과 출력만으로 단위 테스트할 수 있다.

### 5.2 React 어댑터 계층

React 어댑터는 다음 책임을 유지한다.

- 컴포넌트 렌더링과 JSX
- React 훅, 컨텍스트, ref, effect 및 생명주기
- React 이벤트와 DOM 이벤트 연결
- 셀·헤더·필터·그룹 렌더러 계약
- 기존 React 컬럼 정의를 Core 컬럼 모델로 변환하는 어댑터
- 기존 `comins-table` 루트 API의 동작 호환성

React 전용 공개 타입은 루트 진입점에서 제공한다. Core 타입을 React 타입으로 확장하거나 변환할 수는 있지만, Core가 React 타입을 역으로 참조해서는 안 된다.

### 5.3 패키지 경계

0.2.0은 다음 공개 진입점을 유지한다.

- `comins-table`
- `comins-table/core`
- `comins-table/clipboard`
- `comins-table/selection`
- `comins-table/styles.css`

`comins-table/core`는 프레임워크 중립 진입점이 된다. 루트 `comins-table`은 기존 React 제품 진입점으로 유지한다. React가 패키지 peer dependency로 남는 것은 허용하지만, `/core`의 런타임 번들과 선언 파일에는 React 참조가 없어야 한다.

후속 Vue 지원 시 동일 패키지의 별도 진입점, 별도 어댑터 패키지, Core의 별도 패키지화 중 어느 구성이 적절한지는 0.2.0의 실제 Core 사용성과 배포 제약을 근거로 별도 설계한다.

## 6. 호환성 원칙

- 0.1.x 유지보수는 `main`에서 계속하며, 0.2.0 리팩터링을 역으로 섞지 않는다.
- React 사용자의 루트 진입점과 주요 동작은 유지한다.
- `/core`에서 React 전용 타입을 직접 import한 사용자는 0.2.0에서 루트 진입점으로 import 경로를 변경해야 할 수 있다.
- 공개 타입 이동이 발생하면 이전 import와 새 import를 매핑한 마이그레이션 표를 제공한다.
- 제거가 불가피한 공개 계약은 0.2.0 변경 사항에 명시하고, 가능한 경우 호환 별칭 또는 명확한 대체 API를 제공한다.
- 애플리케이션이 소유하는 `data`와 callback 흐름, client-only 경계는 유지한다.

## 7. 브랜치 전략

### 7.1 장기 브랜치

- `main`: 배포 중인 0.1.x와 긴급 수정의 기준선
- `codex-0.2.0-core-separation`: 0.2.0 Core 분리와 React 어댑터 리팩터링의 유일한 통합 브랜치

0.2.0 하위 단계마다 새 기능 브랜치나 worktree를 만들지 않는다. 각 단계는 독립적으로 검토·되돌리기 가능한 커밋으로 구분한다.

### 7.2 0.1.x 수정 유입

0.1.x 긴급 수정이 필요하면 `main` 기준으로 처리한다. 수정이 0.2.0에도 필요한 경우 검증된 커밋만 `codex-0.2.0-core-separation`에 forward-port한다. 충돌 해결 과정에서 0.2.0 구조를 0.1.x에 역이식하지 않는다.

### 7.3 후속 Vue 브랜치

Vue 브랜치는 0.2.0이 검증·통합·배포된 뒤의 `main`에서 생성한다. 0.2.0 브랜치에서 미완성 Vue 코드를 병행하지 않는다.

## 8. 단계별 진행 목록

### 단계 1. 내부 기반 분리 — 완료

- 공유 타입과 React 전용 타입 분리
- UI 역참조 제거
- 순수 계산 일부 추출
- 전체 검증과 소비자 smoke 확인

### 단계 2. 공개 Core 경계 고정

- 현재 `/core` 공개 값·타입과 React 결합 지점 목록화
- React 미설치 타입 소비자와 런타임 import에 대한 실패 테스트 작성
- Core 공개 계약과 React 전용 계약의 이동·호환성 표 확정
- 공개 진입점 inventory 테스트 보강

완료 기준은 실패 테스트가 현재 결합을 재현하고, 목표 계약과 마이그레이션 범위가 코드 변경 전에 고정되는 것이다.

### 단계 3. Core 상태 및 모델 완성

- 프레임워크 중립 컬럼 모델 확정
- 상태 정규화와 controlled/uncontrolled 조정 로직 이전
- 정렬, 필터, 그룹화, 선택, 확장, 편집 상태 전이의 Core 소유권 확정
- 행 모델과 가상화 계산의 UI 독립성 확보

완료 기준은 해당 기능을 React 렌더링 없이 Core 단위 테스트만으로 검증할 수 있는 것이다.

### 단계 4. React 어댑터 전환

- 기존 React 컬럼과 렌더러 계약을 Core 모델에 연결
- React 훅과 DOM 동작은 어댑터 계층에 한정
- 기존 React 동작과 callback 순서의 회귀 검증
- 직접 Core 접근을 전제로 한 내부 UI 코드를 어댑터 경유 구조로 정리

완료 기준은 React 공개 API의 동작을 보존하면서 Core에서 React 역참조가 사라지는 것이다.

### 단계 5. 공개 산출물과 문서 정리

- `/core` 런타임 번들과 선언 파일의 React 무관성 검증
- 루트 및 모든 서브패스 export 검증
- 영어·한국어 Core 사용법과 0.2.0 마이그레이션 문서 동기화
- 루트 React 소비자와 Core 전용 소비자 smoke 수행

### 단계 6. 릴리스 준비 검증

- 관련 단위·타입·빌드·보안·라이선스 검증
- UI 경로 변경분의 focused Playwright 검증
- 스크롤·가상화·메모리 계약 변경분의 성능 검증
- 최종 `npm run verify:full` 단일 실행
- 변경 사항, 잔여 호환성 리스크, 릴리스 체크리스트 정리

이 단계가 완료되어도 원격 push, PR, 병합, 버전 변경 및 배포는 별도 승인 후 수행한다.

## 9. 검증 전략

### 9.1 Core 독립성

- React 패키지와 React 타입을 사용할 수 없는 소비자 fixture에서 `/core` 타입 검사
- `/core` 런타임 import graph에 `react`, `react-dom`, JSX 런타임이 없는지 검사
- 생성된 `/core` 선언 파일에 React 타입 참조가 없는지 검사
- 공개 export inventory 스냅샷 또는 계약 테스트

### 9.2 동작 호환성

- 상태 전이와 행 모델은 Core 단위 테스트로 검증
- React 어댑터는 기존 unit/UI 테스트로 callback, 렌더링, 키보드·포인터 동작을 검증
- UI, 스크롤, 가상화 또는 생명주기 변경이 있는 단계에서만 관련 Playwright·성능 테스트를 실행
- 의미 있는 코드 또는 테스트 계약 변경 후 `npm run verify`를 실행
- 릴리스 준비 시 `npm run verify:full`을 한 번 실행

### 9.3 소비자 검증

- 기존 React 소비자가 루트 진입점으로 빌드·실행되는지 확인
- Core 전용 소비자가 React import 없이 타입 검사와 런타임 import를 통과하는지 확인
- 공개 tarball 기준으로 로컬 소스와 배포 산출물의 차이를 점검

## 10. 완료 기준

0.2.0 Core 분리는 다음 조건을 모두 만족해야 완료로 판단한다.

1. `/core` 공개 소스, 번들, 선언 파일에 React 참조가 없다.
2. Core 상태와 모델의 핵심 동작을 React 없이 검증할 수 있다.
3. 기존 React 루트 API와 지원 동작의 회귀 검증이 통과한다.
4. 기존 공개 진입점이 유지되고 export inventory 검증이 통과한다.
5. 영어·한국어 사용자 문서와 마이그레이션 문서가 동기화된다.
6. Core 전용 및 React 소비자 smoke가 통과한다.
7. 최종 전체 게이트가 통과하고 미실행·실패 항목이 없다.
8. Vue 코드와 Vue 의존성이 0.2.0 변경에 포함되지 않는다.

## 11. 주요 리스크와 대응

### React 컬럼 타입 결합

현재 컬럼 정의와 테이블 상태가 React 렌더러 타입을 통해 결합되어 있을 수 있다. Core 컬럼 모델과 React 컬럼 타입의 상속·변환 방향을 단방향으로 고정하고, `/core` 선언 파일 검사를 회귀 게이트로 둔다.

### 공개 타입 이동에 따른 호환성

`/core`에서 React 전용 타입을 사용하던 소비자는 import 변경이 필요할 수 있다. 타입별 이동표, 변경 예제, 대체 import를 제공하고 불필요한 이름 변경은 하지 않는다.

### 단일 패키지의 설치 의존성

0.2.0에서는 패키지 설치 단위의 React 분리까지 보장하지 않는다. 이를 Core 코드 독립성과 혼동하지 않도록 문서에 명시하고, 실제 Vue 어댑터 설계에서 별도 패키지화 필요성을 다시 평가한다.

### 장기 브랜치 드리프트

0.2.0 브랜치가 길어질수록 `main`과의 차이가 커질 수 있다. 0.1.x 수정은 필요한 커밋만 forward-port하고, 각 단계 종료 시 기준선 차이와 충돌 가능성을 점검한다.

## 12. 확정한 의사결정

- 0.2.0은 Core 분리와 React 어댑터 리팩터링에 집중한다.
- Vue 3 지원은 0.2.0 이후 별도 버전으로 진행한다.
- 0.2.0에는 추가 장기 브랜치를 만들지 않는다.
- `codex-0.2.0-core-separation`을 유일한 0.2.0 통합 브랜치로 사용한다.
- 0.2.0에서는 단일 npm 패키지를 유지하고, 별도 Core 패키지는 후속 설계로 미룬다.
- `/core`는 코드·런타임·타입 수준에서 React와 독립적이어야 한다.
- 구현은 단계별 원자적 커밋과 검증 증거로 관리한다.
