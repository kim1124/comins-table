## 1. 결론

0.1.9는 디자인 언어 및 문서 신뢰성을 중심으로 하되, 현재 Playground 검증에서 확인된 런타임 결함과 예제 UX 문제를 함께 수정하는 유지보수 릴리스로 진행한다.

핵심 결과물은 다음 여섯 가지다.

1. 공개 스타일 계약을 정의하는 루트 `DESIGN.md`
2. 공통 기능의 renderer, formatter, component, slot, CSS token 경계를 정의하는 컴포넌트화 가이드
3. 기능 상태와 API, 가이드, Playground, 테스트 근거를 연결하는 Canonical Feature Manifest
4. 공개 export, 코드 예제, CSS token, 언어별 가이드와 README가 실제 구현에서 벗어나지 않게 하는 자동 검증
5. Header Group 순서 복원, Row Group 가로 스크롤, 다중 Cell 선택과 Row Drag lifecycle의 확인된 동작 보완
6. 기존 Playground 예제의 controlled 상태, toggle 대비, event feedback와 누락된 회귀 검증 보완

기존 데이터 소유권과 호환 가능한 공개 API는 보존한다. 공개 API 확장이 필요한 다중 Cell 선택과 Row Drag lifecycle은 기존 selection 및 event 계약에 추가하는 방식으로 제한하고, 문서 신뢰성 기반과 동일한 검증 근거를 갖춘다.

## 2. 확정된 제품 결정

- 0.1.9에는 문서 신뢰성 작업과 함께 승인된 런타임 결함 및 Playground UX 수정만 포함한다.
- 별도의 대형 기능, 신규 route 또는 구조 재설계는 추가하지 않는다.
- 문서의 양보다 공개 API와 실제 동작에 대한 정확성을 우선한다.
- 루트 `DESIGN.md`는 공개 스타일 계약으로 작성하고 npm package artifact에도 포함한다.
- 컴포넌트화 가이드는 `docs/design/componentization.md`에 둔다.
- 하나의 기능 manifest가 `shipped`, `experimental`, `planned`, `unsupported` 상태를 소유한다.
- `planned`는 별도로 승인된 기능에만 사용한다. 후보 기능을 자동으로 공개 약속으로 바꾸지 않는다.
- 현재 공개 export를 자동으로 조사하고, 새 export가 문서 분류 없이 추가되면 검증을 실패시킨다.
- Markdown TypeScript 예제는 compile 대상과 설명용 fragment를 명시적으로 구분한다.
- 문서 전용 변경에는 관련 없는 E2E를 요구하지 않는다. Playground route, README demo 또는 실제 UI 동작이 바뀔 때만 영향을 받은 E2E를 실행한다.
- `package.json`의 문서 검사 script, version과 package file 변경 및 lockfile의 package version 변경은 browser gate에서 제외한다. dependency, export, runtime, build 또는 기타 미분류 필드 변경은 기존처럼 browser gate를 선택한다.
- Playground route는 추가하지 않지만 기존 Header Groups, Column Pinning, Selection & Clipboard, Rows와 Row Grouping 예제는 확인된 동작과 feedback을 정확히 보여주도록 수정한다.
- Playground는 현재 실행 상태를 유지하고 배포 승인 시점까지 사용자 확인에 사용한다.
- 조사 기록이나 비교 자료는 공개 문서, PR, package artifact에 포함하지 않는다.
- Summary Row의 visible-column `colSpan`은 이미 공개 API, 예제와 테스트가 존재하므로 중복 구현하지 않고 신뢰성 근거만 유지한다.
- Row Grouping의 모든 Detail 접기는 현재 재현 검증에서 정상 동작했으므로 회귀 테스트를 먼저 추가하고, deterministic 실패가 확인될 때만 제품 코드를 수정한다.
- Row Drag lifecycle callback은 사용자가 지정한 `onBeforeRowDrag`, `onRowDrag`, `onAfterDragRow` 명칭을 사용한다.

- README의 Chrome/Edge 지원 범위와 실제 Playwright Chromium 자동 검증 범위가 구분되어 있지만, 지원 근거의 강도를 구조화하지 않는다.

### 3.3 Playground 및 런타임 검증 결과

- 동적 Header Group 예제에서 Group 자식 Column을 `columns` prop에서 제거한 뒤 복원하면 기존 위치가 아니라 마지막 위치에 추가된다. 일반 `columnLayout.groups[groupId].hidden` 방식은 순서를 유지하지만 prop reconciliation은 제거된 ID의 위치를 잃는다.
- Column Pinning의 grouped 예제에서 Body를 가로로 900px 스크롤하면 Row Group content도 같은 거리만큼 이동하여 Group title과 controls가 viewport 왼쪽 밖으로 가려진다.
- Shift Cell 선택은 직사각형 range를 표시하지만 Ctrl/Cmd Cell 선택은 Row만 다중 선택하고 Cell focus는 하나만 유지한다. 현재 `CominsSelectionState`에는 불연속 다중 Cell을 표현하는 필드가 없다.
- Rows event 예제에는 Row Drag handle이 있지만 Drag lifecycle callback과 Alert feedback이 없다.
- Row Grouping 예제에서 Detail 두 개를 펼친 뒤 모든 Detail 접기를 실행하면 Detail DOM은 2개에서 0개로 정상 변경된다. 기존 E2E가 해당 action을 검증하지 않아 회귀 근거가 부족하다.
- Summary Row `colSpan`은 `summary.columns[columnId].colSpan`으로 이미 구현되어 있고 Playground에서 native `colspan="2"`와 covered Cell 제거가 확인된다.
- 관련 기존 Playwright 6개 spec의 22개 테스트는 모두 통과했다. 현재 성공은 위 결함이 없다는 증거가 아니라 실제 순서, geometry, 다중 Cell border, Drag lifecycle과 Detail 전체 접기 assertion이 빠져 있음을 보여준다.

### 5.1 `DESIGN.md`

`DESIGN.md`는 Comins Table의 공개 디자인 계약을 설명한다.

- 제품 시각 원칙과 비목표

- Table frame, Header, Body, Cell, Summary, Group, Detail, pinned zone, overlay, menu, Tooltip, drag feedback
- rest, hover, active, focus-visible, selected, disabled, loading, invalid, drag source, valid drop, rejected drop
- theme inheritance, light/dark behavior, density와 container responsive 규칙
- CSS token 안정성 등급과 SemVer 경계

`package.json.files`에 `DESIGN.md`를 추가한다. README는 npm과 GitHub 양쪽에서 접근 가능한 절대 GitHub 링크를 제공한다.

### 5.2 `docs/design/componentization.md`

컴포넌트화 가이드는 다음 선택 기준을 정의한다.

- formatter: 값의 표시 문자열 변환
- renderer: Header, Cell 또는 Group content의 React 표현 교체
- built-in component: Table이 상태, event isolation과 접근성 계약을 소유하는 경량 UI
- slot: Table 주변 구조나 교체 가능한 surface를 위한 typed component boundary
- CSS token: 여러 instance에 적용되는 시각 계약
- className/style hook: 특정 instance 또는 business state의 최종 override

공통 계약에는 controlled ownership, typed payload, generic 보존, class/style forwarding, portal 소유권, focus 복원, keyboard/ARIA, disabled state, event propagation, public export와 SemVer 기준을 포함한다.

### 5.3 Canonical Feature Manifest

`docs/feature-manifest.json`을 문서 기능 상태의 단일 근거로 사용한다. runtime에서 import하지 않으며 문서 검증에서만 읽는다.

각 기능은 최소한 다음 필드를 가진다.

```json
{
  "id": "column-pinning",
  "status": "shipped",
  "category": "header-layout",
  "apiSymbols": ["CominsColumnPinned"],
  "guides": {
    "en": "docs/user/22-column-pinning.md",
    "ko": "docs/ko/22-column-pinning.md"
  },
  "playgroundRoutes": ["/examples/column-pinning"],
  "tests": [
    "test/column-pinning.test.ts",
    "test/playwright/specs/column-pinning.spec.ts"
  ]
}
```

검증 규칙은 다음과 같다.

- `shipped`: API 또는 documented behavior, 양쪽 가이드, 필요한 Playground route와 focused test 근거가 있어야 한다.
- `experimental`: 불안정 경계와 변경 가능성을 문서에 명시해야 한다.
- `planned`: 별도 승인된 미래 기능만 허용하고 현재 API 또는 shipped catalog에 나타나면 실패한다.
- `unsupported`: 현재 제한 또는 의도적인 비지원 근거를 제공하고 shipped 문구와 충돌하면 실패한다.

Manifest 안의 `publicApi` section은 package entry point별 export를 `documented`, `reference`, `deprecated` 중 하나로 분류한다. 공개 export에는 `internal` 상태를 사용하지 않는다. 내부용 symbol이 실제 package에서 export되고 있다면 호환성 정책을 별도로 결정하기 전까지 public reference로 취급한다.

## 6. 자동 검증 설계

### 6.1 문서 계약 checker

신규 `scripts/check-documentation-contract.mjs`가 다음을 검사한다.

1. Manifest schema와 중복 ID
2. 가이드, route, test evidence path 존재
3. `example/src/docs/featureRouteManifest.ts`와 shipped route의 일치
4. 영문·한글 가이드 basename 및 기능 mapping 일치
5. README의 shipped/unsupported 문구와 manifest 상태 충돌
6. package entry point별 실제 export와 `publicApi` 분류의 일치
7. `styles.css` custom property와 token 안정성 분류의 일치
8. 문서 코드 블록의 compile/fragment annotation 누락
9. 공개 문서와 package artifact에 포함되면 안 되는 자료 경로 및 표현

기존 dependency의 TypeScript Compiler API와 Node 표준 모듈만 사용한다. 새로운 parser package를 추가하지 않는다.

### 6.2 공개 export inventory

- `src/index.tsx`, `src/core.ts`, `src/clipboard.ts`, `src/selection.ts`의 module export를 TypeScript Compiler API로 조사한다.
- runtime value와 type-only export를 모두 inventory에 포함한다.
- root re-export와 subpath export를 entry point별로 구분한다.
- 새 export가 manifest 분류 없이 추가되거나 제거된 export가 manifest에 남으면 실패한다.
- 모든 export의 상세 튜토리얼을 강제하지 않는다. `documented`는 기능 가이드에서 설명하고 `reference`는 API reference에서 정확한 signature와 용도를 제공한다.

### 6.3 코드 예제 typecheck

TypeScript/TSX fenced block 바로 앞에 다음 annotation 중 하나를 사용한다.

```md
<!-- comins-doc-example: compile=quick-start -->
<!-- comins-doc-example: fragment -->
```

- `compile=<id>` 예제는 `test/typecheck/docs/`의 같은 ID fixture와 내용이 일치해야 한다.
- fixture는 기존 TypeScript typecheck에 포함한다.
- `fragment`는 일부 props나 문맥만 설명하는 코드이며 copy-ready 예제로 표현하지 않는다.
- annotation이 없는 TypeScript/TSX block은 검증 실패로 처리한다.
- 첫 단계에서는 Quick Start, Core State, Column Pinning, Row Grouping, Column Filtering, Cross-Table Drag의 최소 사용 예제를 compile 대상으로 삼는다.

### 6.4 CSS token inventory

- `styles.css`에서 `--comins-table-*` 변수를 전수 추출한다.
- `DESIGN.md` 또는 manifest token section에서 모든 변수를 `public-stable`, `public-experimental`, `internal` 중 하나로 분류한다.
- 공개 token은 설명, 적용 surface와 fallback 또는 default를 제공한다.
- internal token은 사용자 가이드의 권장 override 목록에 나타나면 실패한다.
- 새로운 CSS token이 분류 없이 추가되면 실패한다.

### 6.5 언어별 의미 계약

영문과 한글 prose를 문자열로 동일하게 만들지 않는다. 대신 manifest에서 기능 상태, API symbol, Playground route, 제한 ID를 공유하고 양쪽 문서가 같은 ID를 참조하게 한다.

주요 제한은 구조화된 ID로 관리한다.

- `client-only`
- `tree-no-pagination`
- `grouping-single-depth`
- `filtering-no-remote-loading`
- `transfer-duplicate-default-reject`
- `fill-helper-no-visual-handle`

각 언어 가이드가 해당 제한 ID에 대응하는 문단을 포함하는지 checker가 검증한다.

## 7. README 신뢰성 계약

README는 모든 세부 route를 나열하는 API reference가 아니라 소비자용 제품 개요로 유지한다.

- Feature Catalog 제목 또는 설명에 대표 기능 요약임을 명시한다.
- 전체 shipped 기능 목록은 Canonical Feature Manifest와 언어별 인덱스로 연결한다.
- Loading and performance 항목에서 Infinite Scroll과 Lazy Load의 실제 route 및 가이드를 누락하지 않는다.
- public export 전체 목록은 README에 중복하지 않고 API reference로 연결한다.
- `Support`는 `Supported contract`, `Automated evidence`, `Outside contract`를 구분한다.
- Chrome/Edge는 compatibility contract, Playwright Chromium은 자동 검증 근거로 표현한다.
- planned 또는 unsupported 기능을 shipped capability 행에 넣지 않는다.

2. Column Pinning과 Row Group
   - 단일 native `<th scope="rowgroup" colSpan>` 구조는 유지한다.
   - 내부 Group content와 controls를 Body viewport 시작점에 sticky 처리한다.
   - 기본 및 custom Group content가 가로 스크롤 양 끝에서 가려지지 않고 interactive 상태를 유지하는지 검증한다.
3. Ctrl/Cmd 다중 Cell 선택
   - 기존 Row toggle을 유지하면서 불연속 Cell도 함께 toggle한다.
   - plain click은 단일 Cell, Shift는 기존 직사각형 range, Ctrl/Cmd는 Cell set으로 구분한다.
   - 기존 `cell`은 focus와 단일 Clipboard 기준으로 유지하고 호환 가능한 다중 Cell 상태를 추가한다.
   - 이번 범위에서는 불연속 Cell set을 Clipboard matrix로 변환하지 않는다.
4. Row Drag lifecycle
   - `onBeforeRowDrag`는 gesture 등록 전에 호출하고 명시적 취소를 지원한다.
   - `onRowDrag`는 raw pointer event마다 호출하지 않고 target identity 또는 validity가 의미 있게 바뀔 때 호출한다.
   - `onAfterDragRow`는 시작된 gesture마다 한 번 호출하고 moved, cancelled 또는 rejected 결과와 source/target identity를 전달한다.
   - 같은 Table, 다른 Group과 Cross-Table gesture에서 같은 lifecycle payload를 사용하되 Cross-Table model 변경은 기존 Coordinator가 계속 소유한다.
5. Playground
   - Header Group 예제 Row Drag는 `onChangeData`에 연결된 controlled Row 배열로 실제 순서를 유지한다.
   - toggle은 pressed 상태에서 mint 배경과 흰색 글자, released 상태에서 흰 배경과 검은 글자를 사용한다.
   - Rows 마지막 예제 Alert에서 Row Drag lifecycle과 payload를 확인할 수 있게 한다.
   - Row Grouping의 모든 Detail 접기는 visible 및 folded Group 안의 Detail 상태를 모두 clear하는 회귀 테스트를 추가한다.
   - Summary Row `colSpan`은 기존 예제와 테스트를 유지하고 별도 런타임 변경을 하지 않는다.

## 11. 리스크와 통제

### 공개 export inventory 비용

모든 type과 helper를 상세 튜토리얼로 만들면 문서가 과도하게 커질 수 있다. `documented`와 `reference`를 구분하되 package에서 export되는 symbol을 근거 없이 internal로 분류하지 않는다.

### 코드 예제 마이그레이션 비용

모든 fragment를 독립 실행 예제로 바꾸지 않는다. copy-ready 계약이 필요한 예제부터 compile fixture에 연결하고 나머지는 fragment로 명시한다.

### CSS token의 호환성 확대

현재 노출된 66개 변수를 모두 stable로 선언하지 않는다. 실제 사용자 override 대상으로 문서화된 token만 stable 후보로 삼고 나머지는 experimental 또는 internal로 분류한다.

### Manifest 자체의 수동 drift

Manifest 존재만으로 신뢰성을 주장하지 않는다. 실제 source export, styles, route와 파일 system에서 역으로 대조해 누락 시 검증을 실패시킨다.

### 테스트 범위 확장

문서 신뢰성 작업만 변경한 commit에는 관련 없는 브라우저 검증을 추가하지 않는다. 런타임 또는 Playground 변경 commit은 component/public API focused test와 직접 관련된 E2E를 먼저 실행하고, 마지막 shared interaction 변경 뒤 전체 E2E를 한 번 실행한다. OS 재현 환경이나 성능 테스트로 자동 확대하지 않는다. checker 또는 typecheck 실패는 문서 계약 문제로, bind/PATH 문제는 실행 환경으로 분류하고 affected check만 재실행한다.

change-scope classifier는 승인된 field-aware 규칙을 사용한다. `package.json`에서는 `version`, `files`, `scripts.check:docs`, `scripts.verify`만 browser gate 제외 대상으로 허용하고, lockfile에서는 최상위 package version과 root package version만 제외한다. dependency, export, runtime, build 또는 그 밖의 필드 변경은 browser gate를 선택한다. Git 비교 범위나 JSON을 읽지 못하는 경우에도 browser gate를 선택하는 fail-closed 정책을 유지한다.

이번 브랜치에서는 classifier, contract test와 workflow 자체가 browser/policy 입력이고 실제 Playground/UI도 변경되므로 PR 검증에서 Chromium E2E가 선택된다. 이는 우회 대상이 아니라 변경된 라우팅 계약과 제품 동작에 대한 검증이다. 로컬에서도 affected E2E와 마지막 전체 E2E를 worker 1로 실행하되, visual sticky 수정이 scroll engine 변경으로 확대되지 않는 한 성능 테스트는 추가하지 않는다.

Playground는 현재 실행 상태를 유지하고 배포 승인 시점까지 사용자 확인에 사용한다.
